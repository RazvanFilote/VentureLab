# Bronze — Assignment 3 Database Walkthrough

This document maps each Bronze database requirement to the exact files in
`backend/` and proves the schema is in 3NF.

```
backend/
├── app/
│   ├── db/
│   │   ├── session.py          ← SQLAlchemy engine + session factory (env-driven URL)
│   │   ├── models.py           ← ORM classes (Idea, User, Offer, Feedback, Milestone, OfferStatusAudit)
│   │   └── init_db.py          ← runs Alembic migrations on app startup
│   ├── store/                  ← thin wrappers over the ORM (router-facing API unchanged)

├── alembic/
```

## 2. ORM-driven migration

The schema is defined exactly **once** — as Python classes in
`app/db/models.py`. Alembic introspects `Base.metadata` and emits the DDL.
There is no hand-written `CREATE TABLE` in this project. Re-generating the
schema is just:

```bash
# bring an empty DB up to head
alembic upgrade head

# whenever you change a model, generate a new migration from the diff
alembic revision --autogenerate -m "add column X to ideas"
alembic upgrade head
```

`app/db/init_db.py` runs `alembic upgrade head` on app startup, so booting
the FastAPI server against an empty database is enough — no manual SSMS
script needed.

## 3. 3NF proof

A relation is in **3NF** iff:

> for every functional dependency `X → A`, either `X` is a superkey, or `A`
> is part of some candidate key. Equivalently, no non-key attribute is
> transitively dependent on the primary key.

We walk through every table and show this holds.

### 3.1 `users`

| Column   | Type         | Notes                                  |
|----------|--------------|----------------------------------------|
| **id**   | CHAR(36) PK  | UUID                                   |
| name     | VARCHAR(100) |                                        |
| email    | VARCHAR(255) | UNIQUE                                 |
| password | VARCHAR(255) |                                        |
| role     | VARCHAR(32)  | enum: Admin / StartupOwner / Investor  |

- **1NF.** All columns are atomic; no repeating groups.
- **2NF.** `id` is a single-column PK, so no partial dependencies are
  possible.
- **3NF.** No transitive dependencies — none of `name`, `email`, `password`,
  `role` determine any other non-key column. `email` is also a candidate
  key (UNIQUE), and the only thing it determines is the row itself.

### 3.2 `ideas`

| Column      | Type         | Notes                       |
|-------------|--------------|-----------------------------|
| **id**      | CHAR(36) PK  | UUID                        |
| title       | VARCHAR(200) |                             |
| industry    | VARCHAR(32)  | enum                        |
| stage       | VARCHAR(32)  | enum                        |
| description | VARCHAR(2000)|                             |
| created_by  | VARCHAR(100) | name of the startup owner   |
| created_at  | DATE         |                             |

- **1NF / 2NF.** Same single-column PK argument.
- **3NF.** No non-key column determines another non-key column. `created_by`
  is *not* a FK to `users.id`; it is a denormalised display string. We keep
  it as a string deliberately because the relationship "user owns idea" is
  not part of the Bronze scope. (If we promoted it to a FK in Silver, the
  table would still be in 3NF — `created_by_user_id → name` would be a FK
  lookup, not a transitive dependency.)

### 3.3 `offers`  ← critical for 3NF

| Column        | Type            | Notes                                              |
|---------------|-----------------|----------------------------------------------------|
| **id**        | CHAR(36) PK     | UUID                                               |
| idea_id       | CHAR(36) FK     | → ideas.id, ON DELETE CASCADE                       |
| investor_name | VARCHAR(100)    |                                                    |
| amount        | FLOAT           |                                                    |
| equity        | FLOAT           |                                                    |
| message       | VARCHAR(1000)   |                                                    |
| status        | VARCHAR(16)     | enum: Pending / Accepted / Rejected                |
| created_at    | DATE            |                                                    |

> **Removed for 3NF:** the in-memory store carried `idea_title` on every
> offer. That column is functionally dependent on `idea_id`, *not* on the
> offer's PK, which makes it a transitive dependency:
>
>     id → idea_id → idea_title    (BAD — 3NF violation)
>
> So we dropped it. The wire format still contains `idea_title` for
> frontend convenience — `app/store/offers_store.py:_offer_to_dict()` joins
> on `ideas` at serialization time.

After removal, every non-key attribute depends only on `offers.id`.
**3NF holds.**

### 3.4 `feedback`

| Column     | Type           | Notes                |
|------------|----------------|----------------------|
| **id**     | CHAR(36) PK    | UUID                 |
| idea_id    | CHAR(36) FK    | → ideas.id, CASCADE  |
| user       | VARCHAR(100)   |                      |
| rating     | INT            | 1..5                 |
| comment    | VARCHAR(500)   |                      |
| created_at | DATE           |                      |

- 1NF/2NF/3NF — same single-column-PK argument; no column determines
  another.

### 3.5 `milestones`

| Column      | Type           | Notes                                      |
|-------------|----------------|--------------------------------------------|
| **id**      | CHAR(36) PK    | UUID                                       |
| idea_id     | CHAR(36) FK    | → ideas.id, CASCADE                         |
| title       | VARCHAR(200)   |                                            |
| description | VARCHAR(1000)  |                                            |
| status      | VARCHAR(16)    | enum: Pending / InProgress / Done          |
| due_date    | DATE NULL      |                                            |
| created_at  | DATE           |                                            |

- All non-key columns depend only on `milestones.id`. **3NF holds.**

### 3.6 `offer_status_audit`  *(populated by trigger)*

| Column      | Type         |
|-------------|--------------|
| **id**      | INT IDENTITY |
| offer_id    | CHAR(36)     |
| old_status  | VARCHAR(16)  |
| new_status  | VARCHAR(16)  |
| changed_at  | DATE         |

- Trivially in 3NF (audit log; no transitive dependencies).

### 3.7 Summary

| Table                | 1NF | 2NF | 3NF |
|----------------------|-----|-----|-----|
| users                | ✓   | ✓   | ✓   |

## 4. Stored procedures and triggers

All defined in **`alembic/versions/0002_procs_triggers.py`** and applied
when running `alembic upgrade head` against SQL Server. The migration is a
**no-op** on SQLite, which is how the unit-test suite runs against a
lightweight local DB.

### Stored procedures

| Procedure                  | Purpose                                                                    |
|----------------------------|----------------------------------------------------------------------------|
| `sp_global_stats`          | One-row aggregate: total ideas/offers/feedback/milestones, accepted/pending/rejected, average rating, completed milestones. |
| `sp_owner_percent(@id)`    | OUTPUT param returns `100 - sum(equity of accepted offers for @id)`.       |
| `sp_idea_stats(@id)`       | Per-idea aggregate: total/accepted/pending/rejected offers, owner_percent, avg rating, milestone completion. |

`app/routers/stats.py` calls them via `EXEC sp_…` when the dialect is mssql,
falling back to ORM aggregation otherwise (so SQLite tests still pass).

### Triggers (on `offers`)

| Trigger                                | Type             | What it enforces                                                              |
|----------------------------------------|------------------|-------------------------------------------------------------------------------|
| `trg_offers_validate_equity`           | INSTEAD OF INSERT | Rejects an INSERT whose `equity` > 100 − sum(equity of accepted offers for the same idea). Defense in depth: even a direct `INSERT` from SSMS is validated. |
| `trg_offers_status_audit`              | AFTER UPDATE     | Whenever `status` changes, writes `(offer_id, old_status, new_status, today)` into `offer_status_audit`. |
| `trg_offers_block_accepted_delete`     | INSTEAD OF DELETE | Refuses to delete a row whose status is `Accepted`. The application returns 409 first; the trigger guarantees the rule even on direct DB access. |

## 5. Tests

### CRUD / filters / pagination — `tests/test_*.py` (98 tests)

Run against SQLite by default — no SQL Server needed:

```bash
cd backend
python -m pytest tests/ --ignore=tests/test_db_procs_triggers.py -v
```

These cover every endpoint × HTTP verb × Pydantic rule, the same matrix
that was 88% covered before the DB switch.

### Stored procedures and triggers — `tests/test_db_procs_triggers.py` (6 tests)

These need SQL Server. Point `DATABASE_URL` at an empty test database and
run only this file:

```bash
set DATABASE_URL=mssql+pyodbc://@localhost\SQLEXPRESS/venturelab_test?driver=ODBC+Driver+17+for+SQL+Server&trusted_connection=yes
python -m pytest tests/test_db_procs_triggers.py -v
```

The fixture applies all migrations (so schema + procs + triggers are in
place), then exercises:

- `sp_global_stats` — aggregated counters
- `sp_owner_percent` — OUTPUT parameter math
- `sp_idea_stats` — per-idea EXEC
- `trg_offers_validate_equity` — INSERT bypassing the API still rejected
- `trg_offers_status_audit` — UPDATE writes to the audit table
- `trg_offers_block_accepted_delete` — DELETE bypassing the API still rejected
